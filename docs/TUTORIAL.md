# آموزش ساخت برنامه صبحانه

این راهنما برای ضبط ویدیو نوشته شده است. هر بخش یک قسمت از ویدیوست.

## قسمت ۱: برنامه چه کاری می‌کند؟

- **ادمین:** صبحانه، مواد اولیه، کالری، وضعیت بیماری‌ها و کافه‌ها را وارد می‌کند.
- **کاربر:** ثبت‌نام می‌کند، صبحانه را می‌بیند، طرز تهیه و کالری را می‌خواند.
- **کاربر دو راه دارد:** مواد اولیه را بخرد و خودش درست کند، یا از کافه و رستوران سفارش بدهد.

**تشبیه برای ویدیو:** برنامه مثل یک رستوران است.

| بخش برنامه | در رستوران | کارش |
|---|---|---|
| Next.js (`Breakfast.Web`) | منو و میز | چیزی که کاربر می‌بیند |
| Controller (`WebApi`) | گارسون | سفارش را می‌گیرد و جواب را برمی‌گرداند |
| Service (`BusinessLogic`) | سرآشپز | قانون‌ها و تصمیم‌ها |
| Repository (`DataAccess`) | انباردار | خواندن و نوشتن در دیتابیس |
| MySQL | انبار | نگهداری اطلاعات |

مسیر هر درخواست همیشه همین است:

```
صفحه ← Controller ← Service ← Repository ← دیتابیس
```

## قسمت ۲: طراحی دیتابیس

جدول‌های جدید در `DataAccess/Models`:

| جدول | چه چیزی نگه می‌دارد | رابطه |
|---|---|---|
| `Breakfast` | نام، توضیح، طرز تهیه | |
| `BreakfastIngredient` | ماده، مقدار، کالری، قیمت | هر صبحانه چند ماده دارد |
| `BreakfastHealthInfo` | بیماری، مناسب هست یا نه، توضیح | هر صبحانه چند ردیف بیماری دارد |
| `Restaurant` | نام، نوع، آدرس، تلفن | |
| `RestaurantBreakfast` | قیمت صبحانه در آن مکان | چند به چند |
| `Order` | سفارش کاربر | |

**سه نکته‌ی آموزشی:**

1. **چرا کالری کل را ذخیره نکردیم؟** چون از جمع کالری مواد به‌دست می‌آید. اگر جدا ذخیره شود، با تغییر یک ماده عدد غلط می‌ماند.
2. **چرا بیماری جدول جداست؟** اگر ستون `IsForDiabetics` می‌ساختیم، برای هر بیماری جدید باید دیتابیس را تغییر می‌دادیم. حالا ادمین فقط یک ردیف اضافه می‌کند.
3. **چرا `RestaurantBreakfast` لازم است؟** یک کافه چند صبحانه دارد و یک صبحانه در چند کافه هست. قیمت هم به همین رابطه تعلق دارد، چون هر کافه قیمت خودش را دارد.

**چرا `Order` نام صبحانه را هم ذخیره می‌کند؟** تا اگر ادمین صبحانه را حذف کرد، تاریخچه‌ی سفارش کاربر از بین نرود.

## قسمت ۳: ثبت‌نام و ورود

1. موقع ثبت‌نام، رمز با BCrypt هش می‌شود. هش یک‌طرفه است، پس رمز اصلی در دیتابیس نیست.
2. موقع ورود، رمز واردشده با هش مقایسه می‌شود.
3. سرور یک **توکن JWT** می‌دهد؛ مثل کارت ورود که نام و نقش کاربر رویش نوشته شده و سرور امضایش کرده است.
4. فرانت توکن را در هدر `Authorization` هر درخواست می‌فرستد ([api.ts](../Breakfast.Web/src/lib/api.ts)).

**ادمین چطور ساخته می‌شود؟** ثبت‌نام عمومی همیشه نقش `User` می‌دهد. `DataSeeder` هنگام اجرا، ادمین را از بخش `Admin` فایل `appsettings.json` می‌سازد.

## قسمت ۴: Controller و دسترسی‌ها

```csharp
[HttpGet("all-breakfast")]            // همه می‌بینند
[HttpPost] [Authorize]                // فقط کاربر واردشده
[HttpPost] [Authorize(Roles = "Admin")] // فقط ادمین
```

بدون توکن جواب `401` می‌آید و با نقش اشتباه جواب `403`.

**نکته‌ی امنیتی برای ویدیو:** مخفی کردن دکمه‌ی ادمین در فرانت امنیت نیست. امنیت واقعی همین `[Authorize]` روی سرور است.

## قسمت ۵: Service و قانون‌ها

بهترین مثال [OrderService.cs](../BusinessLogic/Services/OrderService.cs) است:

- خرید مواد: `جمع قیمت مواد × تعداد`
- سفارش از کافه: `قیمت همان کافه × تعداد`

**قیمت هرگز از فرانت گرفته نمی‌شود.** اگر می‌گرفتیم، کاربر می‌توانست با دستکاری درخواست، قیمت را صفر کند.

نوشتن سفارش با نام کاربر داخل توکن انجام می‌شود، نه نامی که کاربر می‌فرستد.

## قسمت ۶: DTO و AutoMapper

DTO فرم خروجی و ورودی API است؛ مدل دیتابیس مستقیم بیرون نمی‌رود. مثلاً `BreakfastDetailDto` فیلد `TotalCalories` دارد که در دیتابیس نیست و در [BreakfastProfile.cs](../BusinessLogic/Mapping/BreakfastProfile.cs) محاسبه می‌شود.

## قسمت ۷: فرانت‌اند

| مسیر | صفحه |
|---|---|
| `/` | لیست صبحانه‌ها |
| `/breakfast/1` | طرز تهیه، کالری، بیماری‌ها، خرید و سفارش |
| `/login` و `/register` | ورود و ثبت‌نام |
| `/orders` | سفارش‌های من |
| `/admin` | پنل ادمین |

هر صفحه یک الگو دارد: با `useEffect` داده را می‌گیرد، در `useState` نگه می‌دارد و با `map` نمایش می‌دهد.

در پنل ادمین، مواد اولیه به این شکل وارد می‌شود (هر خط یک ماده):

```
تخم‌مرغ | 2 | عدد | 156 | 30000
```

و بیماری‌ها:

```
دیابت | بله | توضیح
```

عددها را در این فرم با رقم انگلیسی وارد کنید.

## قسمت ۸: برنامه‌ی هفتگی

کاربر برای هر روز هفته یک صبحانه انتخاب می‌کند و برنامه لیست خرید کل هفته را می‌سازد.

- جدول `WeeklyPlanItem`: هر ردیف یعنی «این کاربر، این روز، این صبحانه». روز ۰ شنبه است.
- یک **ایندکس یکتا** روی `(Username, Day)` نمی‌گذارد کاربر برای یک روز دو صبحانه داشته باشد.
- لیست خرید در [PlanService.cs](../BusinessLogic/Services/PlanService.cs) با LINQ ساخته می‌شود:

```csharp
items.SelectMany(i => i.Breakfast.Ingredients)   // همه‌ی مواد همه‌ی روزها
     .GroupBy(i => new { i.Name, i.Unit })        // مواد هم‌نام کنار هم
     .Select(g => g.Sum(i => i.Amount))           // مقدارها جمع می‌شوند
```

**چرا مقدار را به عدد و واحد جدا کردیم؟** متن «۲ عدد» را نمی‌شود جمع زد، ولی `2` و `عدد` را می‌شود. نکته‌ی آموزشی: داده را به شکلی ذخیره کنید که بعداً بتوانید با آن محاسبه کنید.

کاربر با یک دکمه کل لیست خرید را سفارش می‌دهد و در کنار هر روز، اگر صبحانه برای بیماری‌ای نامناسب باشد، هشدار می‌بیند.

## قسمت ۹: اجرای برنامه

**۱. دیتابیس.** MySQL باید روشن باشد:

```
dotnet ef database update -p DataAccess -s WebApi
```

**۲. بک‌اند:**

```
dotnet run --project WebApi --launch-profile http
```

Swagger روی `http://localhost:5179/swagger` باز می‌شود.

**۳. فرانت‌اند:**

```
cd Breakfast.Web
npm install
npm run dev
```

برنامه روی `http://localhost:3000` باز می‌شود. Next.js مسیرهای `/api` را به بک‌اند می‌فرستد ([next.config.js](../Breakfast.Web/next.config.js)).

## سناریوی نمایش در پایان ویدیو

1. با ادمین وارد شوید و یک صبحانه و یک کافه اضافه کنید.
2. خارج شوید و یک کاربر جدید ثبت‌نام کنید.
3. صبحانه را باز کنید و کالری و وضعیت دیابت را نشان دهید.
4. یک بار مواد اولیه بخرید و یک بار از کافه سفارش دهید.
5. در «سفارش‌های من» هر دو را نشان دهید.
6. با ادمین وضعیت سفارش را به «تحویل شد» تغییر دهید.

## چیزهایی که در این نسخه نیست

- **پرداخت آنلاین:** سفارش فقط ثبت می‌شود.
- **سبد خرید:** هر سفارش یک صبحانه دارد.
- **تمدید خودکار توکن:** بعد از ۶۰ دقیقه کاربر دوباره وارد می‌شود.
- **داده‌های نمونه:** قیمت‌ها، کالری‌ها و وضعیت بیماری‌ها فقط برای نمایش هستند و باید با منبع معتبر یا متخصص تغذیه جایگزین شوند.
